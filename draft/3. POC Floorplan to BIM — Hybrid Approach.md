# 3\. POC Floorplan to BIM — Hybrid Approach

## 1. Executive summary

The POC answers two questions: **can we turn a scanned residential floorplan into a usable BIM model automatically**, and **what does a modern, agent-driven UX around that conversion feel like?** Both answers are demonstrated end-to-end on real plans.

The core design decision is a **hybrid architecture**: a deterministic computer-vision engine owns *all geometry* (wall coordinates, room polygons, opening positions), while a vision-language model (Claude) acts as a *semantic layer* on top — labeling rooms, classifying doors vs. windows, reading scale annotations, and reviewing quality. We tested the alternative (asking a VLM to extract geometry directly) and rejected it permanently: coordinates came back with 5–15% error, hallucinated walls, and broken topology. The hybrid split gives us the reliability of classical CV with the flexibility of an LLM where it is actually strong.

On top of the converter we built the full demo experience an internal stakeholder saw in the Higharc "Homebuilding AI" video: a chat-driven conversion with live progress narration, natural-language model edits behind human approval gates, photoreal renders of the 3D view, automatic quantity takeoff with cost chips, and a procedurally enriched model (fixtures, furniture, finish floors, hip roof, exterior envelope) — everything visible in a browser viewer built on the ThatOpen/IFC open-source stack.

> **⚠️ The one-sentence caveat for the room:** the parsing model we used (CubiCasa5K) is licensed **CC BY-NC** — perfect for this demo, **not shippable commercially**. The production path is retraining an MIT-licensed architecture on our own annotated plans (§9, §12).

## 2. Goals & scope

**In scope (locked at kickoff)**

- Single-storey, orthogonal ("Manhattan"), clean residential plans
- IFC4 output: walls with thickness, doors/windows (best-effort), slab, spaces
- Manual scale input as primary; VLM scale reading as backstop
- Deterministic CV geometry + VLM semantics (labels/types only)

**Explicitly out of scope**

- Noisy scans, curved/diagonal walls, multi-storey buildings
- Classical OCR scale chains (superseded by the VLM scale reader)
- **VLM-for-geometry — permanently.** Coordinates stay CV-derived.

Mid-POC, scope was deliberately extended (via ADR-0001) to include *model enrichment* — deterministic furniture layout, fixtures from the drawing, roof and exterior envelope — because the demo target shows a "finished home", not bare walls. Enrichment follows the same rule: every placement is computed deterministically; the LLM never invents geometry.

## 3. System architecture

The repo holds two deliverables that compose into one demo:

| Deliverable | Stack | What it does |
| --- | --- | --- |
| **Floorplan → BIM pipeline** (`floorplan_to_bim`, `f2b` CLI) | Python 3.11 · PyTorch · OpenCV · Shapely · IfcOpenShell · FastAPI | Image → masks → vector model → scaled model → IFC4. Exposed as a CLI and as an HTTP API (`f2b-serve`) with sync and async (SSE-narrated) conversion endpoints. |
| **BIM viewer module** (`@bim/converter`, `@bim/viewer`) | TypeScript pnpm monorepo · Fastify · ThatOpen Fragments · React · three.js | Stateless IFC → `.frag` conversion service (worker-thread pool) + embeddable React viewer components (`<BimViewer>`, properties panel, screenshot API). |

End-to-end data flow:

```
image → [f2b pipeline] → plan.ifc → [@bim/converter POST /jobs] → plan.frag → [<BimViewer>] in the demo app
```

A Vite + React demo app (`apps/viewer-demo`) ties it together. Its default **Agent tab** is the demo surface: upload a plan, watch the agent narrate the conversion over SSE, then chat with the model about edits, renders, and costs.

## 4. Conversion pipeline

Stages communicate only through files on disk (`masks.npz → plan.json → plan.scaled.json → plan.ifc`), which makes every stage independently inspectable and re-runnable.


*(Confluence: attach *`docs/img/f2b-pipeline.png`* from the repo. Blue = CV geometry engine, violet = Claude VLM roles, amber = file artifacts; dashed arrows are best-effort/advisory paths.)*

Stage chain: `parse → vectorize → vlm-enrich → overlay → scale → furnish → ifc → vlm-qa`

**Stage notes**

- **parse** — one pretrained multi-task model (CubiCasa5K) yields wall masks, room segmentation, and door/window heatmaps in a single inference. Large plans are tiled at high resolution rather than downscaled, because walls are only 3–10 px wide.
- **vectorize** — skeletonize → axis-snap → merge → junction-snap turns masks into wall centerlines with thickness (distance transform); rooms via connected components + Shapely; fixtures (toilet, sink, bathtub, appliance…) from the model's icon channels.
- **scale** — the pipeline is *pixel-authoritative*: geometry stays in px, and scaling fills parallel `*_mm` fields. Without a resolved scale the API parks the conversion (`awaiting_scale`) and asks the user, rather than guessing.
- **furnish** — a pure, deterministic layout engine places furniture per room label from mm-space templates with Shapely collision checks. Runs post-scale; the one deliberate exception to px-authority (furniture is mm-authoritative, px back-projected for the overlay).
- **ifc** — IfcOpenShell builds the IFC4 hierarchy, plus enrichment: procedural part compositions for fixtures/furniture (LOD \~200, no mesh assets), per-room finish floors, materials, a hip roof computed as a distance-transform heightfield (height = pitch × distance to footprint boundary — works on any Manhattan footprint), and exterior extras (siding, garage door, porch, walkway aprons).

## 5. The VLM semantic layer

Four structured-output roles, each returning schema-validated JSON (`messages.parse` + Pydantic) — never free text, never coordinates:

| Role | Stage | What it may write |
| --- | --- | --- |
| **Room labeling** | vlm-enrich | `room.label` only — corrects the CV model's regionally-biased labels using the source image + an ID-annotated render |
| **Opening classification** | vlm-enrich | `opening.type` only — door / window / generic from image crops |
| **Scale reading** | scale (opt-in) | A scale *reference* (two pixel endpoints + real mm) fed to the same deterministic converter as manual input — a backstop, never the primary |
| **QA review** | vlm-qa | Nothing in the model — an advisory discrepancy report (`qa_report.md`) comparing overlay vs. original |

**Operating principles (each enforced by a test)**

- **Degrade, never crash** — any API/schema failure leaves the CV result in place; with no credentials the whole pipeline runs CV-only.
- **Adapter seam** — all calls go through a `VlmClient` adapter, so a local/self-hosted VLM can replace Claude for confidential deployments without touching role logic.
- **Two credential paths** — `ANTHROPIC_API_KEY` (first-party; default model `claude-opus-5`, switchable via `F2B_VLM_MODEL` in `.env`) or `F2B_BEDROCK_MODEL` (AWS Bedrock inference profile — keeps traffic inside our AWS account, typically the easier compliance story; takes precedence when set).

## 6. Agent experience (the demo layer)

Built in phases against the Higharc demo video as the north star; all merged to main:

| Phase | Capability | How it works |
| --- | --- | --- |
| 1 | **Narrated conversion** | `POST /conversions/async` returns an SSE stream; a read-only Narrator maps pipeline checkpoints to agent events (tool chips, artifacts, metrics) replayable via `Last-Event-ID`. Conversions without scale park and resume. |
| 2a | **NL edits + approval gates** | Claude runs a tool loop over *deterministic* edit operations (relabel, resize, openings, defaults) — the LLM picks the operation and parameters symbolically; Shapely computes the geometry; every mutation requires explicit user approval in the UI. |
| 2b | **Wall topology** | Room merge/split with adjacency and sliver/notch guards — same approval-gated pattern. |
| 3 | **Photoreal rendering** | The `render_image` tool requests a viewer screenshot (capture gate), then a Gemini image model restyles it. Degrades to a friendly message without a key. |
| 4a | **Estimates** | A pure, LLM-free quantity takeoff (`takeoff.py`) over the scaled plan × placeholder unit costs → cost chip + estimate panel + a read-only `get_takeoff` agent tool. (Placeholder prices — not real cost data yet.) |
| 5a | **Interior enrichment** | Drawing-detected fixtures, deterministic furniture layout, materials, finish floors, door/window detail — plus furniture edit tools (move/add/remove) where touched items become *pinned* and survive re-layout. |
| 5b | **Exterior enrichment** | Hip roof (with a viewer toggle), siding, garage door, porch and walkway aprons. |

> **Why the edit design matters:** every edit the agent can make is a **named, deterministic, approval-gated operation**. The LLM chooses *what* to do; plain code computes *where*. This keeps the no-VLM-geometry invariant intact even in the interactive path, and makes every mutation auditable.

## 7. BIM viewer module

- `@bim/converter` — stateless, unauthenticated-by-design IFC → `.frag` HTTP service (Fastify + worker-thread pool). In-memory job registry; restart loses jobs and clients resubmit. Must sit behind the host product's gateway. All config is env vars; internal paths never leak into responses.
- `@bim/viewer` — `ViewerCore` wrapping ThatOpen Fragments + React bindings (`<BimViewer>`, `<PropertiesPanel>`, `useBimViewer`). React 18+ as peer deps; the Fragments web worker is fetched from a CDN by default and should be self-hosted for production.
- Version-coupled deps (`three` / `web-ifc` / `@thatopen/*`) are pinned centrally in the workspace catalog and must move together.

## 8. Engineering quality

- **356 Python tests, all hermetic** — no model weights, no API keys, no network; the full suite runs in \~5 s. VLM calls are dependency-injected and faked.
- **JS side:** unit/integration tests per package plus 12 Playwright e2e specs covering the demo flows (upload → narrate → scale-park → resume → edit → estimate).
- **Invariants are executable** — `docs/invariants.md` pairs each golden rule (VLM never touches geometry, degrade-never-crash, pixel-authority, licensing boundary, takeoff purity…) with the specific test or grep that enforces it.
- **CI** runs the JS build + tests + e2e on GitHub Actions. *Known gap: the Python suite is not in CI yet* — it's run locally per merge.

**Data egress.** Two external calls exist, both acceptable for this POC because it uses **public plans only**: floorplan images go to the Anthropic API (or AWS Bedrock inside our own account), and viewer screenshots (renders of the 3D model, not the source drawing) go to Google's Gemini API for photoreal restyling. A deployment on confidential client drawings must reconfirm policy or swap in a local VLM via the adapter seam — that path is designed in, not bolted on.

## 10. Limitations & known risks

- **Regional bias** — CubiCasa is trained on Finnish plans; accuracy degrades on other drawing styles. Client-style plans must be tested early; the production fix is retraining on client-domain data.
- **Geometry scope** — single-storey, orthogonal walls only. Curved/diagonal walls and multi-storey are out of scope for the POC.
- **Scale is load-bearing** — no IFC without a resolved scale. The UX handles this (park + ask), but fully automatic conversion depends on the VLM scale reader finding a readable annotation.
- **Revit import** — Revit is stricter than IFC viewers (wall joins, opening booleans are the classic failures). Validated in viewers continuously; Revit acceptance needs its own pass before client commitments.
- **No formal accuracy metrics yet** — the planned side-by-side (% walls/openings recovered, dimensional error, vs. the Plans2BIM commercial benchmark) hasn't been executed; quality evidence so far is visual (overlay alignment + VLM QA reports) on the hero plans.
- **Costs are placeholders** — the estimate feature demonstrates the mechanism, not real pricing.

## 11. Commercial context

| Product | Pricing | Output | Notes |
| --- | --- | --- | --- |
| Plans2BIM (WiseBIM) | €15 / plan | IFC + DXF | 10 s – 3 min per plan |
| MakeaBIM | €0.10 / BIM object | IFC | API on Enterprise tier |

These set the bar: roughly 50% modeling-time reduction with mandatory human cleanup. The build-vs-buy question is real — if a commercial service hits the accuracy bar on *our clients'* plans, buying the conversion step and building the experience layer (agent UX, edits, estimates, viewer) on top is a legitimate strategy. What this POC uniquely demonstrates is the experience layer plus full control of the pipeline.

## 12. Production roadmap

1. **Replace the parser** — retrain MitUNet (MIT architecture) on client-style plans; multi-model fusion later.
2. **Confidentiality path** — local/self-hosted VLM behind the existing `VlmClient` adapter; Bedrock path already works today.
3. **Accuracy evaluation** — the deferred metrics table on client plans, including the commercial-service benchmark and a Revit acceptance pass.
4. **Feature backlog** — construction sheets (FR-9), prompt-started designs (FR-1.1), real cost data for takeoff, multi-storey and non-Manhattan support.
5. **Hardening** — Python suite into CI, self-hosted Fragments worker, single-parse optimization in the converter.
